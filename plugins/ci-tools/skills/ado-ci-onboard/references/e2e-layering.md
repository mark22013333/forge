# 測試分層與 E2E 執行原則

CI 不需要每次都把所有測試跑一遍。依「多快能得到回饋」和「會不會動到共用資料」分成四層，每層有自己的觸發時機。

## 四層

| 層 | 內容 | 觸發時機 | 失敗時 |
|----|------|----------|--------|
| 單元 | 不需外部資源的測試；可用「只跑近期修改」縮短時間（踩坑 12） | 每次 push | 擋下這次建置 |
| 冒煙 | 部署後打幾個關鍵端點或頁面，確認服務活著、主要流程能走 | 每次部署到測試環境後 | 通知並視情況回退部署 |
| 回歸 | 完整的 E2E 情境 | 每晚排程 | 隔天處理，不擋白天的 push |
| 完整 | 單元＋整合＋全部 E2E | 手動觸發（發版前） | 擋下發版 |

原則：

- 單元層要快。整套跑太久時，先用 `forkEvery = 1` 與排除清單把結果穩定下來，再用近期修改篩選縮短時間，不要直接拿掉測試。
- 需要資料庫或外部設定檔才能跑的測試屬於整合測試，不放在單元層（踩坑 9）。
- 被暫時排除的測試要寫明原因與移除條件（見 `ci-init.gradle` 的 `EXCLUDED_TESTS`）。

## E2E 的執行環境

E2E（例如 Playwright）會改動測試環境的資料，兩個 E2E 同時跑會互相干擾。

- **獨立 agent pool**：E2E 專用一個 pool，不和單元建置搶 agent。
- **序列化**：同一個測試環境一次只跑一個 E2E。可以在 environment 的 Exclusive lock 檢查搭配 `lockBehavior: sequential`，或讓 E2E pool 只有一個 agent。
- 多 agent 並行只適用於不改共用資料的建置（踩坑 22）。

本期不提供 E2E pipeline 範本。
